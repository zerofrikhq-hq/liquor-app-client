1. EXECUTIVE SUMMARY & CORE REQUIREMENTS
================================================================================
Chillbro is a premium, on-demand alcohol delivery marketplace in Sydney, NSW,
operating under strict 18+ age verification compliance and 30–45 minute express
delivery SLAs.

The mobile application must provide a seamless end-to-end shopping experience:
- Auth: Email & Password authentication with DB-stored 6-digit OTP confirmation
  for both Registration and Forgot/Reset Password flows.
- Vendor Marketplace: Browse verified licensed vendors (Kumar K, Siva, John, etc.)
  with delivery radius and ETA.
- Storefront & PDP: Multi-category product exploration under the selected vendor,
  with ABV, bottle sizes, volume variant selections, pricing, and live inventory.
- Single-Vendor Cart Enforcement: Strict single-vendor cart constraint. Attempting
  to add an item from a different vendor prompts an explicit Overwrite/Cancel dialog.
- Persistent Database Cart: Carts are backed by PostgreSQL, ensuring omnichannel
  continuity across mobile and web.
- Checkout & Payments: Address input, delivery notes, and Stripe payment integration.
- Order History & Inventory: Real-time inventory adjustment upon order placement
  and tracking order status in a dedicated "My Orders" interface.
- Profile Management: Customer profile editing and security settings.

3. POSTGRESQL DATABASE SCHEMA ADDITIONS & DDL
================================================================================

The existing database already contains `users`, `user_roles`, `otps`, `vendors`,
`products`, `categories`, `brands`, and `notifications`.

To satisfy all user requirements, we will apply the following atomic schema
additions:

--------------------------------------------------------------------------------
-- 3.1 Role & Customer Identity
--------------------------------------------------------------------------------
INSERT INTO user_roles (id, code, name, description, is_active)
VALUES (3, 'CUSTOMER', 'Customer', 'End-user mobile delivery customer', true)
ON CONFLICT (id) DO NOTHING;

--------------------------------------------------------------------------------
-- 3.2 Omnichannel Persistent Cart Tables
--------------------------------------------------------------------------------
-- Represents the active shopping session for a customer.
-- Enforces: One active cart per user, locked to exactly one vendor at a time.
CREATE TABLE IF NOT EXISTS carts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  vendor_id BIGINT REFERENCES vendors(id) ON DELETE SET NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS cart_items (
  id BIGSERIAL PRIMARY KEY,
  cart_id BIGINT NOT NULL REFERENCES carts(id) ON DELETE CASCADE,
  product_id UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  selected_volume VARCHAR(100), -- e.g. "700mL", "10ml", "Case of 6"
  unit_price NUMERIC(10,2) NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT unique_cart_product_variant UNIQUE (cart_id, product_id, selected_volume)
);

CREATE INDEX IF NOT EXISTS idx_cart_items_cart_id ON cart_items(cart_id);

--------------------------------------------------------------------------------
-- 3.3 Orders & Order Items Tables
--------------------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS orders (
  id BIGSERIAL PRIMARY KEY,
  public_id UUID DEFAULT gen_random_uuid() NOT NULL UNIQUE,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  vendor_id BIGINT NOT NULL REFERENCES vendors(id) ON DELETE RESTRICT,
  status VARCHAR(50) DEFAULT 'placed' NOT NULL, 
  -- Statuses: placed, confirmed, preparing, out_for_delivery, delivered, cancelled
  subtotal NUMERIC(10,2) NOT NULL,
  delivery_fee NUMERIC(10,2) DEFAULT 0.00 NOT NULL,
  tax_amount NUMERIC(10,2) DEFAULT 0.00 NOT NULL,
  total_amount NUMERIC(10,2) NOT NULL,
  delivery_address TEXT NOT NULL,
  contact_phone VARCHAR(50) NOT NULL,
  delivery_instructions TEXT,
  payment_status VARCHAR(50) DEFAULT 'pending' NOT NULL, -- pending, paid, failed, refunded
  payment_method VARCHAR(50) DEFAULT 'stripe' NOT NULL,
  stripe_payment_intent_id VARCHAR(255),
  estimated_delivery_time TIMESTAMP WITH TIME ZONE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL
);

CREATE TABLE IF NOT EXISTS order_items (
  id BIGSERIAL PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id UUID NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  product_name VARCHAR(255) NOT NULL,
  sku VARCHAR(100) NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(10,2) NOT NULL,
  subtotal NUMERIC(10,2) NOT NULL,
  selected_volume VARCHAR(100),
  created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_orders_user_id ON orders(user_id);
CREATE INDEX IF NOT EXISTS idx_orders_vendor_id ON orders(vendor_id);
CREATE INDEX IF NOT EXISTS idx_order_items_order_id ON order_items(order_id);

4. REST API SPECIFICATION & ENDPOINT CONTRACTS
================================================================================

All endpoints return JSON with consistent envelope semantics:
`{ "success": boolean, "message"?: string, "data"?: any, "error"?: string }`

--------------------------------------------------------------------------------
4.1 Authentication & Profile
--------------------------------------------------------------------------------
- POST /api/auth/register-request
  Payload: { email, password, full_name, phone_number }
  Action:  Generates 6-digit OTP, stores bcrypt-hashed password & data in `otps` payload.
           Sets `form_context = 'customer_registration'`.

- POST /api/auth/verify-registration-otp
  Payload: { email, otp_code }
  Action:  Validates OTP from `otps` table. If valid, inserts record into `users` with
           role_id=3 (CUSTOMER). Marks OTP `is_used = true`. Returns JWT/User.

- POST /api/auth/login
  Payload: { email, password }
  Action:  Validates credentials via bcrypt. Returns customer user record and auth token.

- POST /api/auth/forgot-password-request
  Payload: { email }
  Action:  Verifies user exists. Generates 6-digit OTP in `otps` with `form_context = 'password_reset'`.

- POST /api/auth/reset-password-verify
  Payload: { email, otp_code, new_password }
  Action:  Verifies OTP, hashes new_password, updates `users.password_hash`. Marks OTP used.

- GET /api/user/profile?userId=:id
  Action:  Returns user profile details (name, email, phone, role).

- PUT /api/user/profile
  Payload: { userId, full_name, phone_number }
  Action:  Updates profile information in `users`.

--------------------------------------------------------------------------------
4.2 Vendors & Storefront
--------------------------------------------------------------------------------
- GET /api/vendors
  Action:  Returns all active vendors (id, business_name, description, address, contacts, product_count).

- GET /api/vendors/:id
  Action:  Returns single vendor profile, address, operating details.

- GET /api/vendors/:id/products
  Action:  Returns all products belonging to `vendor_id = :id` with category mappings,
           brand details, volume options, pricing, and live inventory (`qty`, `is_in_stock`).

- GET /api/products/:id
  Action:  Returns full product details (PDP), gallery images, tasting notes, volume variants.

--------------------------------------------------------------------------------
4.3 DB-Backed Cart Operations (Single-Vendor Enforcement)
--------------------------------------------------------------------------------
- GET /api/cart?userId=:userId
  Action:  Returns current cart, assigned vendor, and array of populated cart items with
           subtotal, delivery fee ($9.99 or free over $100), and total.

- POST /api/cart/items
  Payload: { userId, vendorId, productId, quantity, selectedVolume, overwrite }
  Logic:
    a) If user has no active cart, create cart with `vendor_id = vendorId`. Add item.
    b) If cart exists with SAME `vendor_id`, add or increment product quantity.
    c) If cart exists with DIFFERENT `vendor_id`:
       - If `overwrite !== true`: Return HTTP 409 Conflict with payload:
         { conflict: true, currentVendor: { id, name }, newVendor: { id, name } }
       - If `overwrite === true`: Truncate existing `cart_items`, update `cart.vendor_id = vendorId`,
         and insert the new product.

- PUT /api/cart/items/:itemId
  Payload: { userId, quantity }
  Action:  Updates quantity. If quantity === 0, deletes the row. Recalculates cart.

- DELETE /api/cart/items/:itemId?userId=:userId
  Action:  Removes item. If cart is now empty, sets `cart.vendor_id = null`.

- DELETE /api/cart?userId=:userId
  Action:  Clears all items and resets `cart.vendor_id = null`.

--------------------------------------------------------------------------------
4.4 Checkout & Orders
--------------------------------------------------------------------------------
- POST /api/payments/create-intent
  Payload: { userId, deliveryAddress, contactPhone }
  Action:  Validates cart, checks live inventory stock, calculates total amount in cents,
           and initiates a Stripe PaymentIntent. Returns `clientSecret`.

- POST /api/orders/place
  Payload: { userId, deliveryAddress, contactPhone, deliveryInstructions, paymentIntentId }
  Logic (Executed inside a single DB Transaction):
    1. Read and lock all cart items (`SELECT FOR UPDATE`).
    2. Verify `products.qty >= cart_item.quantity` for every item.
    3. Insert row into `orders`.
    4. Insert rows into `order_items`.
    5. Deduct inventory:
       `UPDATE products SET qty = qty - $1, is_in_stock = (qty - $1 > 0) WHERE id = $2`
    6. Delete items from `cart_items` and reset `cart.vendor_id = null`.
    7. Commit transaction and return order confirmation with estimated delivery.

- GET /api/orders/user/:userId
  Action:  Returns customer's order history sorted by `created_at DESC` with full item lists.

- GET /api/orders/:orderId
  Action:  Returns detailed tracking info, live status, and vendor details for a specific order.

5. CORE BUSINESS LOGIC & STATE MACHINES
================================================================================

--------------------------------------------------------------------------------
5.1 Single-Vendor Cart Locking & Overwrite Resolution
--------------------------------------------------------------------------------
State Machine Flow:
1. User browses "Vendor A" (e.g. Siva) and taps "Add to Cart" on Cedar Peak Whisky.
   -> Cart is locked to Vendor A.
2. User returns to marketplace and browses "Vendor B" (e.g. Kumar K).
3. User taps "Add to Cart" on Lemon Bacardi.
4. Client checks current `cart.vendorId`:
   `cart.vendorId !== newProduct.vendorId` (Conflict Detected!)
5. The App intercepts the action and shows a modal:
   +-------------------------------------------------------------+
   |                  Replace Cart Items?                        |
   | You already have items from "Siva" in your cart.            |
   | Ordering from "Kumar K" will clear your current cart.       |
   |                                                             |
   |        [ Cancel / Keep Current ]   [ Clear & Add Item ]     |
   +-------------------------------------------------------------+
6. If "Cancel":
   - Modal closes. Cart remains unchanged. New item is not added.
7. If "Clear & Add Item":
   - API called with `{ overwrite: true }`.
   - Server flushes Vendor A's items, updates `cart.vendor_id = Vendor B`,
     and adds Lemon Bacardi.
   - Haptic feedback and confirmation toast displayed.

--------------------------------------------------------------------------------
5.2 DB-Backed Omnichannel Persistent Cart
--------------------------------------------------------------------------------
- All cart additions, deletions, and quantity adjustments immediately synchronize
  with PostgreSQL tables `carts` and `cart_items`.
- If the customer logs into the web platform or another device, the exact cart
  state (including volume variant and vendor lock) is preserved.

--------------------------------------------------------------------------------
5.3 OTP Lifecycle Engine
--------------------------------------------------------------------------------
- Generation: 6-digit cryptographically secure pseudorandom number (`100000 - 999999`).
- Expiry: 10 minutes (`expires_at = NOW() + INTERVAL '10 minutes'`).
- Storage: Saved into `otps` table with `form_context` (`customer_registration` or
  `password_reset`), `identifier` (user email), and JSONB `payload`.
- Developer/Testing Mode: Since SMS/SMTP gateways require third-party keys, the OTP
  is persisted in PostgreSQL and returned in the API response in dev mode so testing
  can be executed directly without external telecom delays.

--------------------------------------------------------------------------------
5.4 Atomic Inventory Deduction & Concurrency
--------------------------------------------------------------------------------
To prevent overselling when multiple customers check out concurrently:
```sql
BEGIN;

-- Lock and verify stock
SELECT id, name, qty FROM products 
WHERE id = ANY($product_ids) 
FOR UPDATE;

-- Decrement quantity with safety boundary
UPDATE products 
SET 
  qty = qty - $ordered_qty,
  is_in_stock = (qty - $ordered_qty > 0),
  updated_at = CURRENT_TIMESTAMP
WHERE id = $product_id AND qty >= $ordered_qty;

-- If rows affected == 0, abort and raise "Insufficient Stock"
COMMIT;
```
